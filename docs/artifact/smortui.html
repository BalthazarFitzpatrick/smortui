smortui

The shared web interface for a family of local tools: one stylesheet and a dozen plain scripts a small Python server hands out, so every tool looks and behaves like one product. No build step, no framework, no npm. Every control on this page is drawn by that stylesheet and those scripts, loaded unchanged.

the six rules that carry the look

They live in base.css's header, where someone about to override something will be looking. Override by redefining tokens, never by fighting the rules.

  1. 1one row height, app-wide--row-height sizes every row and every button, so nothing reads as a different size class
  2. 2one clickable class.toggle is a button, a list row, a filter pill and a dropdown head. A head is a toggle with a caret
  3. 3dividers never touch the edge15px inset, 2px thick, the weight of a button border. A 1px rule beside 2px buttons reads as a different system
  4. 4selection is bright, rejection is mutedrejecting is a decision, not an achievement; giving it the accent makes a wall of rejections look like a wall of wins
  5. 5text stays selectableuser-select: none on controls also makes every name and readout uncopyable, which costs more than the stray drag-select it prevents
  6. 6monospace throughoutthese tools show filenames, counts and coordinates, and those line up or they are not readable
One font size, everywhere. Emphasis is carried by colour (dim, text, cream) and by the row a thing sits in. Size was a third channel saying the same thing less clearly. A test fails the build if a font-size is set anywhere but the token.

the tokens

Named for what they space, not how big they are, so a consumer asks for "the gap between rows" and cannot accidentally ask for eight pixels.

the palette, with its contrast on the ground

Neutrals do the work. Two hues were sampled from photographs of lichen and stone; the rest are derived. The semantic pointers (--status-*, --fill-*, --attention) aim at them, so a repalette moves a pointer and keeps the record of where each colour came from. Contrast is computed live from the loaded stylesheet.

menus: one class, many shapes

One Menu for every popup, built from generic sections, so a new menu is a data structure rather than new code. The class owns anchoring, viewport clamping (and dropping up near the bottom), one menu at a time, dismissal on outside click and Escape, arrow, Enter and Space navigation. onDismiss always fires.

The name takes the room and the stats give way, and both orders have been wrong in turn. Measured on a dataset picker at 1600px: the stats held 157px of a 303px row while the name got 96 and needed 282. Nobody picks a dataset by its counts.

slider and tree

A threshold is a position on a range, not one of seven listed numbers. The distribution drawn over the axis is why: "no results" and "no results because your cut sits above every value in the data" look identical until something shows the shape. The bare .range-slider below it is the same look on a plain input, no makeSlider needed.
renderTree: a grouped list with a status pip and trailing badges pushed to the far edge, so several rows' badges line up as a column. Item state flags become classes; the caller keeps its own styling.

board primitives

buckets with 2D roving focus

focus a row and use the arrow keys
Only the focused row sits in the tab order. Left and right move between buckets, up and down between rows; a shorter bucket clamps to its last row instead of losing focus, and up from the top row exits the grid rather than doing nothing.

card, fan, and the focus glow

Tab or click into a card: it stays exactly where it is while the ones after it slide down, so the item you are reading is never the item that moved. The overlap is a proportion, not a pixel count. The focus glow is four things that are only good together, shipped as one class: the lift, an inset ring, the inner glow, and the coloured light over the whole face. A card is never shrunk; what gives is how the cards meet.

the pile

A desk pile of real cards. Each layer is nudged and turned from its own card's id (pileLayerJitter, a hash rather than Math.random, so the same cards always draw the same pile). The count stays level over the lot. pile.js is all geometry and no DOM: the three regimes, spread, fan, piled, and the fold that eats a card at the pile's own edge.

The expander grows a strip into a centred panel on the same backdrop the modal uses, so it is not a second language for "floating over everything". The drawer parks a sliver at a screen edge and opens into the middle of its half. The badge hides at zero. viewport: pan and zoom

reset view
100% wheel to zoom, drag to pan
Wheel zooms anchored on the pointer, because zooming about a corner walks whatever you are aiming at off screen. Reset centres as well as unzooming: setting the scale back and leaving the pan alone reads as a button that half works. With shift held a browser sends the wheel as deltaX; reading deltaY alone made every shift+scroll take the zoom-out branch.

selection: click, cmd+click, shift+drag, right-click

nothing caught
Plain click picks; it does not toggle a destructive flag. Right-click on something unselected selects it first, so the menu can only ever act on things wearing a visible ring. Shift+drag is a net, not a range: the mismatches you can see sit together on screen, so a rectangle you drag over them is the honest gesture, and it autoscrolls at the edges.

recipes: patterns built from what exists

A recipe never adds a section kind or a file; it documents a shape for composing the primitives above. Each has a live block on this page and in the repo's demo, a doc under docs/recipes/, and an entry in docs/recipes/index.json, a small manifest an agent can read before loading anything else.

the api, per file

Scripts define globals; there are no modules and no imports. base.css first so a tool's own stylesheet can override it; menu.js before anything that opens a Menu; shell.js before the script that calls initShell. Every other script only if you use it.

# ui_base (python)
ASSETS: Path   asset_names() -> list[str]   read_asset(name) -> bytes   content_type(name) -> str   UiBaseError
Teardown. A component that listens on window or document returns destroy(), and it means teardown, not close: no onClose, no onChange, no focus moved. A host that mounts once for the page's life can ignore it; a host that rebuilds must call it, or every rebuild leaves one more listener behind.
